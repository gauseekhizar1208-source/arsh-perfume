ARSH PERFUMEPROJECT HANDBOOK

Project overview

ARSH PERFUME is an India-focused e-commerce website for attars, roll-on perfumes and fragrance oils. It combines a public storefront, customer accounts and an administrator back office in one Laravel application.

Purpose and objectives

  • Help customers discover fragrances, compare available sizes and place orders.
  • Keep product prices, stock, discounts and order totals consistent on the server.
  • Give the store owner tools to manage products, payments, fulfilment, content and reports.
  • Support Cash on Delivery, Razorpay online payments and direct UPI with manual receipt verification.

Users and access

UserMain capabilities
Visitor / guestBrowse, search, manage a session cart, check out when enabled, track an order and contact the store.
CustomerGuest capabilities plus wishlist, saved addresses, profile, password and own order history.
AdministratorRestricted management screens for catalogue, inventory, orders, customers, content, settings and reports.

Scope of this document

This handbook explains the implemented website and how to install, use and maintain it. Appendices contain migration-derived table definitions and the registered application routes. It describes source behavior; it does not certify a production deployment or a real payment-provider integration.

ARSH PERFUMECUSTOMER GUIDE

Customer guide: discovery and cart

Browse and find a fragrance

  1. Open /shop to view the catalogue, or /collections to browse categories.
  2. Search by keyword. Narrow results by category, fragrance family, minimum/maximum price or in-stock availability.
  3. Sort by newest, price ascending, price descending or popularity.
  4. Open a product to read the supplied description, fragrance notes, specifications, images and approved reviews.

Choose a size and add to cart

Prices and stock belong to product variants, such as a bottle size. Choose an active size with a confirmed price and available stock. The cart validates availability; each line allows up to 10 units and remains subject to current stock.

Manage the cart

  1. Open /cart. Adjust quantities or remove an item.
  2. Enter a coupon if you have one. The server checks validity, eligible products, order minimums and usage limits.
  3. Review the subtotal, discount, shipping, tax information and final amount.
  4. Continue to checkout. Availability, stock and current prices are checked again when the order is placed.

Wishlist and reviews

Sign in to save products to the wishlist. Reviews require a delivered purchase of the product and are held for administrator approval. A customer cannot submit multiple reviews of the same product.

Cart continuity

Guests use a browser-session cart. Signed-in users have a persistent cart. The application merges the guest cart during sign-in; the displayed quantities still depend on stock validation.

Customer guide: checkout and tracking

Place an order

  1. Review the cart and continue to /checkout. Sign in if guest checkout has been disabled by the store.
  2. Provide your name, email, phone number and shipping address. The state must match a configured Indian state/territory and the PIN code must have six digits.
  3. Select an available payment method. Review the final amount and submit once.
  4. Complete the method-specific payment instructions. Retain the order number shown on confirmation.
MethodCustomer actionPayment confirmation
Cash on DeliveryPlace the order and pay when collected.Administrator collection or delivery updates payment records.
RazorpayComplete the provider checkout.Verified server callback/webhook; a redirect alone is insufficient.
Direct UPI QRScan/open the payment link and submit the transaction reference.Administrator checks the actual bank receipt before marking paid.

Track and manage orders

Use /track-order with the order number and checkout email. Signed-in customers can also open My Account → Orders to view their own order details and history. Customers may cancel their own orders while pending or confirmed.

Guest order access

The browser session that placed a guest order receives access to its protected storefront pages. Keep the order number and email for the separate tracking lookup. A sequential internal database ID is not a customer access credential.

Customer accounts and Google sign-in

Email accounts

Customers register at /register, sign in at /login and sign out using the logout form. Forgotten-password and token-based reset screens are provided. Account screens support profile updates, password changes and saved-address management.

Optional Google sign-in

  • Laravel Socialite handles the Google OAuth redirect and callback.
  • Google sign-in remains unavailable until a Client ID and Client Secret are configured.
  • A new public Google registration creates a customer account, never an administrator.
  • Verified Google email and a stable Google account identifier are required.
  • An existing email match does not silently connect accounts. Existing customers sign in locally, then connect Google from My Account after confirming their password.
  • Google-only customers can establish email/password sign-in through the account or password-reset flow.

Configuration example

GOOGLE_CLIENT_ID=your-client-id.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=your-client-secret
GOOGLE_REDIRECT_URI=http://localhost:8000/auth/google/callback

php artisan config:clear

Register the exact callback URI with the OAuth provider. Scheme, hostname, port and path must match the address used to open the store. For production, use the actual HTTPS domain. If no redirect override is set, the application derives it from APP_URL.

Account access

Disabled accounts are blocked and signed out on their next web request. Customer order and address policies restrict records to the owning customer.

ARSH PERFUMEADMIN GUIDE

Admin guide: catalogue and inventory

Access the administration panel

Sign in using an active administrator account, then open /admin. There is no public administrator registration. Provision administrators with the dedicated command described in the installation section.

Create or update a product

  1. Open Products. Enter the name, SKU, category, description and optional fragrance information.
  2. Add one or more variants. Each variant has its own SKU, size, price, sale price, stock and low-stock threshold.
  3. Upload product images and select a primary image. Supported uploads: JPG/JPEG, PNG and WebP, up to 8 files; each at most 3 MB and at least 300 × 300 pixels.
  4. Keep incomplete products as drafts. Publishing requires at least one active variant with a positive price. A sale price must be below the regular price.
  5. Use featured/bestseller flags and supplied SEO fields where appropriate. Save and inspect the public product page.

Categories and stock

Manage category names, slugs, descriptions, images, active status and sort order. A category that still contains products cannot simply be deleted; deactivate it or reassign the products first.

Use Inventory to adjust variant stock and record the reason. The inventory ledger records additions, deductions, reservations, cancellations and stocktake differences. Stock is reserved immediately during order placement, so available stock changes before fulfilment.

CSV support

Product CSV export is implemented. A product import route is registered, but its controller method is absent; CSV product import must not be described as a working feature.

Admin guide: orders and payments

Process an order

  1. Open Orders and review the customer's address, purchased item snapshots, totals and payment state.
  2. Confirm payment where required. Unpaid online orders cannot advance through fulfilment.
  3. Move the order through permitted states: confirm, process, ship, and deliver.
  4. Add courier/tracking details as they become available. Review the recorded history and invoice.

Payment actions

MethodAdministrator responsibility
CODRecord collected cash when appropriate; delivery automatically marks COD payment as collected.
RazorpayUse verified gateway records. Investigate failed or mismatched payments before proceeding.
UPIInspect the receiving bank/UPI account, compare full amount and reference, confirm receipt, then use Verify UPI payment received.

Cancellation, returns and refunds

Cancellation is allowed only by the configured status transition map. Reserved stock is restored once on cancellation. Return restocking is optional. Refunds may be full or partial, up to the remaining refundable amount; a full refund changes the payment status to refunded.

Live Razorpay refunds use the gateway integration. For UPI, transfer the refund separately through the bank/UPI app before recording it in the store. A record-only action does not move money to a customer's bank account.

Direct UPI review

A customer-entered reference is a claim awaiting verification. The same verified bank reference cannot settle two orders. The Razorpay unpaid-order timeout excludes direct UPI orders; cancel stale UPI orders manually when appropriate.

Checkout integrity, pricing and inventory

Transactional placement

  1. Validate checkout fields and the selected method; obtain the cart and optional idempotency key.
  2. Begin a database transaction and lock variants in stable ID order.
  3. Recheck active product/variant status, confirmed prices and available stock.
  4. Lock and revalidate a coupon where supplied. Calculate authoritative totals.
  5. Create the order, item/address snapshots, payment record and status history.
  6. Reserve stock immediately and write inventory movements; clear the cart.
  7. Commit and emit the placed-order event. A repeated idempotency key returns the original order.

Totals

Subtotal is the sum of current unit price × quantity. Discounts are bounded by eligible amounts. Shipping is evaluated against the discounted subtotal and the configured free-shipping threshold. With inclusive tax, the tax portion is informational; with exclusive tax, tax is added to the discounted subtotal. Shipping is then included in the final amount.

Discounted subtotal = subtotal - validated discount
Inclusive-tax total = discounted subtotal + shipping
Exclusive-tax total = discounted subtotal + tax + shipping
Net included revenue = grand total - refunded amount

Preserved purchase history

Order items snapshot product/variant information, quantities and prices. The delivery address is also copied to the order. Later edits to the catalogue or saved address do not rewrite an existing purchase.

Concurrency and stock

The server does not trust a browser-supplied total. Row locks and transactional stock operations protect checkout races. Cancellation uses stock_restored_at to avoid restoring the same reservation twice.

Payment states and operating rules

  • Order payment states: pending, paid, failed and refunded. Individual gateway payment records can use provider/attempt states such as created.
  • Customers can cancel only pending or confirmed orders that they own.
  • Unpaid online orders cannot advance through fulfilment.
  • COD is marked paid on delivery or explicit cash collection.
  • Unpaid Razorpay reservations expire after 30 minutes and are collected by the task running every ten minutes. Actual release occurs on the next successful scheduled run.
  • Direct UPI awaiting review is excluded from that expiry task.

Payment integrations

Razorpay online payments

Configure RAZORPAY_KEY_ID, RAZORPAY_KEY_SECRET and RAZORPAY_WEBHOOK_SECRET on the server. Register POST /webhooks/razorpay as the provider webhook endpoint for capture and failure notifications. Use test credentials before configuring live credentials.

  • The amount comes from the saved order total and is checked against provider values.
  • Checkout callbacks use HMAC-SHA256 over order/payment identifiers; webhooks verify the raw request body.
  • Recorded provider event identifiers make duplicate/retried webhooks idempotent.
  • A successful browser redirect alone never marks an order paid.
  • A simulated gateway exists for local non-production use. Production requires real provider configuration.

Direct UPI QR

Checkout snapshots payee name + UPI ID + order amount
↓
Browser generates a local QR / upi:// payment URI
↓
Customer transfers funds and submits an unverified reference
↓
Administrator verifies actual receipt → payment marked paid

QR generation uses the bundled qrcode library. The code does not call an external QR-image service. References are normalized and must contain 6–64 letters or digits. A verified reference is unique across settled orders.

Financial verification boundary

This documentation run performed no real bank transfer, real Razorpay charge/refund or live Google consent round trip. Automated tests use controlled or simulated integration paths.

Installation: local development

Prerequisites

PHP 8.2+ with the required Laravel/database extensions, Composer 2, Node.js compatible with the installed Vite version, npm and MySQL 8. Vite 7 requires Node 20.19+ or 22.12+ according to its installed package metadata. Enable pdo_mysql, mbstring, openssl, tokenizer, XML/DOM, ctype, fileinfo, curl and GD for the documented functionality; SQLite extensions are needed for the test suite.

Fresh installation in PowerShell

Set-Location C:\xampp\htdocs\arsh-perfume
composer install
# Copy only when .env does not already exist:
Copy-Item .env.example .env
php artisan key:generate
# Create a database, then configure DB_* in .env.
php artisan migrate --seed
npm ci
npm run build
php artisan storage:link
php artisan arsh:create-admin owner@example.com --name="Store Owner"
php artisan serve

The administrator command prompts for a password. Set APP_URL to the address you actually use; the default development address is http://localhost:8000. For day-to-day asset development, run npm run dev in a separate terminal.

XAMPP configuration

Point the Apache virtual host at C:/xampp/htdocs/arsh-perfume/public, enable mod_rewrite and AllowOverride All, and start MySQL. The PHP CLI and Apache PHP configurations may differ. Ensure the web user can write storage and bootstrap/cache. Windows storage-link creation may require Developer Mode or an appropriately privileged terminal.

Fresh setup only

Do not replace an existing .env, regenerate a deployed APP_KEY, reseed owner data or rebuild an existing database just to read this documentation. The handwritten SQL schema predates the Google migration; migrations are authoritative.

Deployment, queues and maintenance

Production release sequence

  1. Prepare PHP, MySQL, HTTPS and a web-server document root pointing to public/. Keep environment secrets outside version control.
  2. Set APP_ENV=production, APP_DEBUG=false, the HTTPS APP_URL and SESSION_SECURE_COOKIE=true.
  3. Install locked PHP dependencies and build frontend assets. Apply migrations using the normal release procedure and an available backup.
  4. Verify the storage link and writable runtime directories. Cache configuration/routes/views/events.
  5. Run the scheduler every minute and maintain a supervised queue worker. Restart workers after a release.
  6. Verify owner content, shipping/tax settings, notifications and payment methods with controlled test orders.

Background processes

# Keep the worker running under a service manager:
php artisan queue:work --sleep=3 --tries=3 --max-time=3600
# Invoke once per minute using cron / Windows Task Scheduler:
php artisan schedule:run

The schedule expires unpaid Razorpay reservations every ten minutes and prunes failed jobs older than 168 hours daily. The built-in health route is /up. Back up the database, uploaded media and deployment configuration; keep protected copies and rehearse restoration. Review application logs and failed jobs regularly.
